# Workflow — Оркестрация документирования проекта

## Назначение

Этот файл описывает процесс автоматического создания компактных `.py.md` файлов-описаний для каждого модуля проекта (файла исходного кода). Используется Hermes Agent (оркестратор) для управления субагентами. Карточка — намёк, а не спека: дешёвая ориентировка вместо чтения исходника. Правила процесса язык-агностичны; примеры даны на Python.

***

## Архитектура процесса

```

     ORCHESTRATOR (ты)
 - Читай файлы задачи 
 - Запускай субагентов 
 - Проверяй результаты 
 - Применяй исправления 
└──────────┬───
           │
     ┌─────▼─────┐
     │  SUBAGENT │ ← читает задачу, обрабатывает файл, сообщает результат
     │   (leaf)  │
     └───────────┘
```

***

## Правила оркестратора

### 1. Вызов субагентов

**Формат команды (минимальный):**

```
Задача: _map/pass1-v2-task.md
Обработать: <путь/к/файлу.py>
Отметить: _map/file-list.md
```

**ПРИМЕЧАНИЕ:** Субагенты часто не справляются с чтением файла задачи. Если результат пустой — дай полный промпт напрямую в `goal`, включая пример результата.

### 2. Последовательность

**СТРОГО ПОСЛЕДОВАТЕЛЬНО: 1 субагент = 1 файл.**

Не запускай батчи параллельно. Каждый файл обрабатывается отдельно:

1. Запусти субагента на файл N
2. Дождись результата
3. Проверь что файл создан и чекбокс отмечен
4. Запусти субагента на файл N+1

### 3. Обработка ошибок

Если субагент не создал файл:

- **Повтори с полным промптом** (не читай файл задачи, вставь пример напрямую)

- Если 2-й раз не удалось — создай файл самостоятельно через `write_file`

- Отметь чекбокс `[x]` в чеклисте вручную через `patch`

### 4. Проверка результата

После каждого субагента проверяй:

1. Файл `.py.md` создан и не пустой
2. Чекбокс `[x]` стоит в чеклисте для этого файла
3. Нет галлюцинаций (проверяй секцию «Расхождения»)

## Формат `.py.md` (Pass 1)

```markdown
# <name>.py — <одно предложение факта: что делает модуль>  |  <timestamp>

## Публичный API

### Функции
#### `func_name(args) -> return_type`
<1-2 предложения: что делает, какие параметры, что возвращает. Только факты из кода.>

### Классы
#### `ClassName`
<1-2 предложения: назначение.>
- **Атрибуты:** <если есть значимые>
- **Методы:**
  - `method(args) -> type` — <описание>
  - `another_method(args) -> type` — <описание>
- **ВАЖНО: Перечисли ВСЕ публичные методы (без `_` в начале). Каждый — отдельная строка.**

## Зависимости (внутренние)
| Импортирует | Из файла | Объекты | Зачем |
|---|---|---|---|
| `name` | `module.py` | `obj1`, `obj2` | <одно предложение: зачем используется> |

## Принцип работы
<2-3 предложения, ТОЛЬКО факты из кода. Без субъективных оценок ("ключевой", "важный", "основной").>

## Внешние зависимости
<Только если агент может не знать что это. Стандартную библиотеку и популярные пакеты пропускай.>

## ⚠️ Расхождения docstring ↔ код
<Если есть противоречия между docstring и реальным кодом — описать здесь. Иначе секцию опустить.>
```

### Критические правила формата:

- **Ноль номеров строк** — убраны полностью, чтобы не путать агента

- **Все публичные методы классов** — перечислены, каждый отдельной строкой

- **Только факты из кода** — никаких "ключевой", "основной", "важный"

- **Проверка docstring vs код** — противоречия фиксируются в секции `⚠️`

- **Целевое сжатие:** 4-10× 

***

## Формат `.py.md` (Pass 2 — аудит и исправление)

Pass 2 НЕ создаёт новые файлы. Агент читает ВСЕ `.py.md` карточки, находит ошибки/мусор/несоответствия и либо исправляет их сам (патчем), либо пишет рекомендации в отчёт.

### Критические правила:

- **ИСПРАВЛЯЙ что можешь сам** — опечатки, мусор в зависимостях, лишние секции

- **Читай** **`.py`** **для сверки** — только если нашёл конкретную проблему и нужно проверить факт

- **НЕ перезапускай Pass 1** — если файл нужно создать заново, напиши рекомендацию оркестратору

- **НЕ меняй формат** **`.py.md`** — только содержимое, не шаблон

- **Цикличность** — оркестратор применяет исправления из отчёта → запускает Pass 2 снова → пока не получит `>> DONE`

***

**Принцип:** Точечные правки существующей карточки (patch), а не перезапись целиком.

## Опциональные хелперы-подсказки (`_map/helpers/`)

Помимо чтения кода, субагент МОЖЕТ (не обязан) воспользоваться языковым хелпером-подсказкой. Если для языка обрабатываемого файла есть хелпер-скрипт в `_map/helpers/`, его можно запустить, чтобы получить структурированную подсказку (список публичных символов, импортов) и свериться с ней. Хелпер — вспомогательная подсказка, а не обязательный шаг и не замена анализу кода. Для Python: `_map/helpers/py_api.py` (`python _map/helpers/py_api.py <путь/к/файлу>`).

## Проверка актуальности карточек

Перед началом работы с проектом (или после изменений в исходниках) запускай проверку:

```bash
python _map/check_freshness.py
```

**Что делает скрипт:**

- Если проект — git-репозиторий: находит исходники, изменённые (в рабочем дереве и/или новее по истории коммитов) без соответствующего обновления их карточки. В выводе сообщает `режим: git`.

- Если гита нет (догитовый проект): фоллбэк на сравнение `mtime` карточки и исходника — карточка старше исходника считается устаревшей. В выводе сообщает `режим: mtime`.

- Выдаёт отчёт со списком устаревших карточек

**Как интерпретировать результат:**

- `✅ ВСЕ КАРТОЧКИ АКТУАЛЬНЫ` — всё хорошо, можно работать

- `❌ НАЙДЕНО N УСТАРЕВШИХ КАРТОЧЕК` — нужно перезапустить Pass 1 для этих файлов

- `⚠️ КАРТОЧКИ БЕЗ ИСХОДНИКА` — карточки существуют, но `.py` файлы удалены

**Что делать при устаревших карточках:**

1. Смотришь список в отчёте
2. Запускаешь Pass 1 для каждого устаревшего файла (как обычно, последовательно)
3. Повторяешь проверку — пока не получишь `✅ ВСЕ КАРТОЧКИ АКТУАЛЬНЫ`

- [ ] Нет параллельных субагентов в данный момент
