# Pass 1 — Создание .py.md файлов-описаний  (Компактный заголовок модуля)

## Роль

Ты — агент-документатор. Твоя задача — прочитать файл исходного кода проекта `<name>` и создать рядом с ним .py.md файл-описание.

**Карточка = намёк, а не спека.** Её задача — дать дешёвую ориентировку по модулю, чтобы другой агент не читал весь исходник. Опирайся на факты из кода; не пытайся описать всё исчерпывающе.

## Входные данные

ты - агент-документатор иследователь, получаеш от Оркестратора файлы с полными путями:

- задание (Этот файл)

- обрабатываемый файл `<WORKSPACE>/<name>`

- списко где отмечать результаты `<list>`



## Файл списка

Читай файл `<list>`.md — в нём перечень всех файлов для обработки. Ты обрабатываеш только свой файл  `<name>` остальные файлы это задача других агентов. После обработки файла отмечай его чекбоксом `[x]`.



## ЦЕЛЬ

Создать / обновить файл `<name>.py.md` рядом с исходным файлом кода, который позволяет другому агенту(не тебе) дёшево, не читая весь исходник, понять:

- зачем этот модуль

- какой у него публичный API

- с чем он связан внутренне

- есть ли расхождения в документации

Карточка должна быть **кратко — в несколько раз меньше исходника**. Ориентир сжатия — **4-10×** (или больше), но это не жёсткий лимит: важнее полнота публичного API, чем экономия строк.

## КРИТИЧЕСКИЕ ПРАВИЛА

### 1. ТОЛЬКО факты из кода

- **НЕ** использовать поняти: "ключевой", "основной", "важный", "главный" и подобные которые — агент не может знать из одного файла

- **НЕ** описывать роль в архитектуре на основе предположений (всегда сверка с кодом обрабатываемого файла `<name>`)

- **НЕ** выдумывать связи, которых нет в импортах (всегда сверка с кодом обрабатываемого файла `<name>`)

### 2. Проверка docstring vs код

Для КАЖДОГО публичного объекта:

1. Прочитай docstring / комментарий-описание объекта, а также обычные коментарии. Отличай закомментированные функции или варианты методов которые по какойто причине отключены но присутствуют в коде, их можно упомянуть одной строчкой в отчёте (факт наличия или альтернативы раелизации или недоделанной реализации).
2. Прочитай реализацию (тело функции/класса)
3. Если есть противоречие — запиши в секцию `⚠️ Расхождения`
4. Если противоречий нет — секцию опустить

**Примеры противоречий:**

- Docstring: "поддерживает local/fastembed" → код разделяет как `"local"` и `"fastembed"`

- Docstring: "возвращает список" → код возвращает кортеж или None

- Docstring: "никогда не raises" → код поднимает исключение

### 3. Что описывать, что нет

**ОПИСЫВАЙ:**

- Все публичные функции и классы (без `_` в начале)

- Публичные атрибуты классов

- Публичные методы классов

- Импорт внешних зависимостей (если агент может не знать)

**НЕ ОПИСЫВАЙ:**

- Приватные функции (`_function_name`)

- Приватные атрибуты (`_attribute`)

- Вспомогательные хелперы

- Номера строк для приватных объектов

### 4. Краткость

- Кратко — в несколько раз меньше исходника (ориентир сжатия 4-10×, без жёсткого лимита строк/токенов)

- Одно предложение на объект

- Таблица зависимостей: одно предложение на строку



## Опциональный хелпер-подсказка

Помимо чтения кода, ты МОЖЕШЬ (не обязан) воспользоваться языковым хелпером-подсказкой. Если для языка обрабатываемого файла есть хелпер-скрипт в `_map/helpers/`, можешь запустить его, чтобы получить структурированную подсказку (список публичных символов, импортов) и свериться с ней. Хелпер — вспомогательная подсказка, а не обязательный шаг и не замена анализу кода. Для Python: `_map/helpers/py_api.py` (запуск: `python _map/helpers/py_api.py <путь/к/файлу>`).

## Порядок действий

1. Прочитай файл по полученным путям и имени `<WORKSPACE>/<name>` (файл исходного кода)
2. Для каждого публичного объекта:
   a. Прочитай docstring
   b. Прочитай реализацию
   c. Проверь на противоречия
3. Составь заголовок по формату выше
4. Запиши результат в `<WORKSPACE>/<name>.py.md`
5. Прочитай `file-list.md`

   - для своего файла который ты получил как задание `<name>` Отметь `[x]` показав что ты выполнил задачу.
6. Сообщи результат
